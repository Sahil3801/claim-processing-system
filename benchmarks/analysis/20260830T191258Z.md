# Analysis of benchmark run 20260830T191258Z

This report contains only values read from
`benchmarks/results/20260830T191258Z`. The run used 10,000 claims, 1,000
claimants, 10 virtual users, 60-second measured trials, 15-second warm-ups, and
one cache-on/cache-off repetition.

## Cache comparison

| Metric | Cache off | Cache on |
|---|---:|---:|
| p50 latency | 110.4966 ms | 190.59923 ms |
| p95 latency | 300.731948 ms | 300.3515058 ms |
| p99 latency | 402.07524796 ms | 395.68383944 ms |
| Throughput | 63.17581829 requests/s | 58.24073257 requests/s |
| HTTP/application error rate | 0 | 0 |
| Measured requests | 3,809 | 3,509 |

Redis reported 3,508 keyspace hits, one miss, no evictions, no expired keys, no
rejected connections, and no Redis error replies during cache-on. The measured
cache hit rate was therefore 3,508 / 3,509, approximately 99.97%. Low hit rate
is ruled out.

PostgreSQL recorded 7,569 commits for 3,809 cache-off requests (approximately
1.99 commits/request) and 3,542 commits for 3,509 cache-on requests
(approximately 1.01 commits/request). Tuple fetches also fell from 8,091 to
3,725. This shows that the claim-detail cache did remove the claim lookup, but
one database transaction remained on nearly every cache hit.

The remaining transaction comes from `JwtAuthenticationFilter`, which calls
the database-backed `UserDetailsService` for every authenticated request. That
behavior keeps account status and role changes effective immediately and is not
being changed merely to improve a benchmark.

Redis itself showed no operational problem. Its command-processing CPU total
was 28,241 microseconds across the measured cache-on interval, with no eviction
or error signal. Generic JSON serialization successfully round-tripped cached
`ClaimDTO` objects. Serialization and the extra network hop may cost more than
an in-memory PostgreSQL primary-key lookup at this 10K scale, but this run does
not isolate or quantify that cost, so it is not a basis for changing the
production serializer.

## Methodology limitations found

1. Only one repetition was run, so order effects and ordinary variance cannot
   be estimated.
2. Ten closed-loop VUs drove an application capped at one CPU. Latencies cluster
   near 100 ms multiples, consistent with possible CPU-quota scheduling under
   load, but the run did not save cgroup throttling counters. This is a plausible
   confounder, not a proven cause.
3. The intended cache-isolation test still included one PostgreSQL-backed JWT
   user lookup per request. It measured end-to-end authenticated behavior, not
   only PostgreSQL-versus-Redis claim retrieval.
4. The mixed API run started the Kafka notification consumer with real SMTP
   defaults. Email attempts failed with Gmail STARTTLS errors, causing Kafka
   retry/DLT stack traces and unrelated CPU/network activity. These errors began
   after the cache comparison, so they did not explain its result, but they did
   contaminate the mixed workload.
5. The k6 setup needs `responseType: "text"` because the read scenario discards
   response bodies globally but must parse the login response. That existing
   correction is retained and now covered by a configuration test.

## Corrections for the next run

- Cache-only trials use two VUs by default and three alternating repetitions.
- A benchmark-profile-only primary `UserDetailsService` supplies the two known
  principals during cache comparison, removing the unrelated authentication DB
  query. Production and mixed-workload authentication remain database-backed.
- Each trial now saves Docker stats and the application cgroup `cpu.stat` before
  and after measurement so throttling can be assessed.
- Redis statistics now also include memory and per-command data.
- The benchmark Kafka consumer is disabled while the producer remains active,
  preventing external email retries from contaminating API measurements.
- A checked-in 10K validation profile and one-command runner fix the next run's
  parameters.

## Index experiment

The separate daily-report index experiment behaved as intended at 10K claims.
Without the index PostgreSQL used a sequential scan, processed 336.143129
transactions/s, and reported 11.900 ms average pgbench latency. With the Flyway
V6 index it used a bitmap index/heap scan, processed 817.598480 transactions/s,
and reported 4.892 ms average latency. These figures describe only this recorded
dataset, selectivity, and host.
