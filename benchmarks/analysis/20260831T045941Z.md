# Phase 16 final performance report: 100K-claim benchmark

Run: `20260831T045941Z` | Analysis date: 2026-08-31

## Executive conclusion

The strongest optimization result is the PostgreSQL date-index comparison: the
bounded daily-report query's pgbench average latency fell from **58.302 ms to
10.205 ms (82.50% lower)**, while throughput rose from **68.608 to 391.946
transactions/s (5.71x, +471.28%)**. The query plan independently confirms less
work. These are local synthetic-benchmark results, not production measurements.

Redis worked: the three measured cache-on detail-read trials recorded **19,946
hits and 329 misses (98.3773% aggregate hit rate)**. However, **a repeatable Redis
latency/throughput improvement is not established**. Medians of trial p95/p99
improved by 21.02%/17.97%, but median p50 worsened by 1.20% and median throughput
fell by 2.28%. Paired trials disagree, and the application was CPU-throttled in
96.49%-98.21% of scheduling periods. Do not turn the favorable median tail values
into an unqualified resume claim that Redis made the application faster.

Across all seven measured API trials, **42,958 requests produced zero unexpected
HTTP statuses (0% observed error rate)**. This is a bounded load-test observation,
not an availability/SLA or full business-correctness guarantee.

No production code, configuration, benchmark workload, or raw results were
modified for this analysis. Phase 17 was not started.

## 2. Cache-off versus cache-on: measured results

All latency values below are milliseconds, taken from `claim_detail_latency`,
not the broader HTTP metric that also includes setup/login. Request rate is the
recorded `claim_detail_requests.rate`. It uses k6's recorded rate denominator;
counts are not simply divided by the nominal 60-second duration. Warmups and
setup requests are excluded from the reported request counts/latency trends.

### Per-trial evidence

| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Cache off r1 | 117.875 | 305.993 | 412.704 | 120.511 | 7,262 | 0% |
| Cache off r2 | 188.828 | 398.423 | 502.181 | 109.340 | 6,590 | 0% |
| Cache off r3 | 188.292 | 388.325 | 496.720 | 114.531 | 6,895 | 0% |
| Cache on r1 | 190.551 | 306.694 | 407.436 | 111.915 | 6,747 | 0% |
| Cache on r2 | 193.508 | 400.596 | 508.374 | 99.997 | 6,028 | 0% |
| Cache on r3 | 110.087 | 302.663 | 405.516 | 124.363 | 7,500 | 0% |

### Medians across the three trials per mode

These are **medians of trial-level percentiles**, not percentiles of pooled
requests. Each trial receives equal weight. Calculations use unrounded values.

| Metric | Cache-off median | Cache-on median | Cache-on change |
| --- | ---: | ---: | --- |
| p50 latency | 188.291539 ms | 190.550671 ms | **1.20% worse** |
| p95 latency | 388.325385 ms | 306.693622 ms | **21.02% lower** |
| p99 latency | 496.720014 ms | 407.436456 ms | **17.97% lower** |
| Throughput | 114.530817 requests/s | 111.915004 requests/s | **2.28% lower** |
| Observed HTTP-status error rate | 0 / 20,747 = 0% | 0 / 20,275 = 0% | No observed difference |

Latency reduction = `100 * (off_median - on_median) / off_median`.
Throughput improvement = `100 * (on_median - off_median) / off_median`.
The unrounded changes are -1.199805%, +21.021485%, +17.974625%, and -2.283938%,
respectively, where positive denotes improvement.

### Why the apparent tail improvement is inconclusive

| Paired repetition | p95 reduction | p99 reduction | Throughput increase |
| --- | ---: | ---: | ---: |
| r1 | -0.229% | +1.276% | -7.133% |
| r2 | -0.546% | -1.233% | -8.545% |
| r3 | +22.059% | +18.361% | +8.584% |

Negative means worse with Redis. Two pairs do not show a p95 improvement; only
r3 shows a large improvement. The median paired p95 percentage change is
actually **-0.229%**, unlike the +21.021% reduction obtained by comparing the two
groups' medians. Both calculations are valid but answer different questions.
With only three short, fixed-order pairs and substantial variation, no stable
causal Redis speedup or regression is established. The fastest single trial
(124.363 requests/s) is not a sustained-capacity or maximum-throughput result.

## 3. Cache, database, and CPU evidence

### Redis works, but this is a small warmed working set

| Cache-on trial | Hits | Misses | Hit rate | Redis keys at capture | Server GET mean |
| --- | ---: | ---: | ---: | ---: | ---: |
| r1 | 6,665 | 82 | 98.7846% | 280 | 6.67 microseconds |
| r2 | 5,897 | 131 | 97.8268% | 278 | 7.62 microseconds |
| r3 | 7,384 | 116 | 98.4533% | 280 | 5.82 microseconds |
| Aggregate | **19,946** | **329** | **98.3773%** | Not additive across resets | Not a pooled mean |

Hit rate = `hits / (hits + misses)`. In each cache-on trial, hits plus misses
exactly equal measured detail requests. Cache-off trials recorded zero hits,
misses, and keys; their hit rate is not applicable. All six cache trials recorded
zero evictions, expirations, rejected connections, and Redis error replies.
Cache-on Redis used approximately 1.24-1.26 MiB against the 96 MB maximum.

`claim-ids.json` contains only **1,000 IDs (1 through 1,000)**, not 100,000.
Furthermore, the same deterministic selector drives both hot/cold choice and
index selection in `claim-read.js`. With `HOTSET_PERCENT=10`, hot reads can reach
only the 80 indices ending in 0-7 within the first 100; cold reads can reach only
the 200 indices ending in 8-9 within all 1,000. The sets are disjoint, giving a
**280-key theoretical maximum**, consistent with the recorded 278-280 keys after
warmup plus measurement. This is a workload-selector limitation, not evidence of
Redis dropping keys. Raw HTTP URL tags are normalized, so they cannot separately
reconstruct per-ID request frequencies.

Therefore, describe the hit rate as a **warmed, small-working-set detail-read
benchmark against a 100K-claim database**, not "98% cache hit rate across 100K
claims" or production traffic. This report documents the limitation without
changing the completed experiment or its workload.

### PostgreSQL work was reduced

| Trial | Cache-off commits | Cache-on commits |
| --- | ---: | ---: |
| r1 | 7,266 | 128 |
| r2 | 6,588 | 171 |
| r3 | 6,881 | 161 |
| Total | 20,735 | 460 |

Normalizing each mode's totals by its request count gives approximately 0.9994
versus 0.02269 observed commits/request: **97.73% lower** with Redis. These are
`pg_stat_database` snapshots, not exact claim-query counts; setup/background
transactions and statistics-flush timing affect them (some off snapshots are
slightly below the HTTP count). Use as supporting evidence of database offload,
not an exact "97.73% fewer SQL queries" resume claim. All six snapshots reported
zero PostgreSQL blocks read, consistent with a hot database-buffer baseline.

### CPU saturation is now measured

Subtracting each before snapshot from its after snapshot:

| Trial | Throttled periods / total periods | Percentage |
| --- | ---: | ---: |
| Cache off r1 | 605 / 616 | 98.21% |
| Cache off r2 | 611 / 626 | 97.60% |
| Cache off r3 | 605 / 627 | 96.49% |
| Cache on r1 | 606 / 622 | 97.43% |
| Cache on r2 | 606 / 627 | 96.65% |
| Cache on r3 | 604 / 615 | 98.21% |
| Mixed API | 630 / 643 | 97.98% |

The one-CPU application consumed roughly 60.6-62.0 CPU-seconds during each cache
measurement capture interval. These intervals also include surrounding runner
overhead; percentages are scheduling periods experiencing throttling, **not
percent wall time lost**. Do not divide cumulative `throttled_usec` by 60 seconds
and interpret it as a wall-time fraction.

This confirms CPU quota pressure in both modes, not that Redis alone caused the
pressure. Redis's server-side microsecond GET execution excludes client network,
Lettuce, serialization, HTTP handling, JWT verification, JVM scheduling, and GC.
There is no profiler/GC trace or client Redis timing to attribute their separate
costs. The run does not establish a serializer defect or a Redis configuration
problem. In particular, the production authentication query was removed from
these cache-isolation trials and is not their remaining database bottleneck.

## 5. PostgreSQL index comparison: strongest optimization result

The existing Flyway V6 B-tree index, `idx_claims_claim_date ON claims(claim_date)`,
was dropped and recreated only in the disposable benchmark database. Other
indexes remained. Both trials ran the same count/sum/average daily aggregation
for `2025-12-01 <= claim_date < 2025-12-08`, grouping by date. Each used 4 clients,
2 threads, simple query mode, a 10-transaction warmup, and 30 measured seconds.

The index comparison followed the mixed API run. Thus the table contained
**100,105 claims**, not exactly 100,000: the 100K seed plus 105 successful creates.
The no-index plan independently confirms 959 matching + 99,146 filtered rows.
The query returned 7 daily groups and selected about 0.96% of the table.

| Measurement | Without date index | With date index | Measured change |
| --- | ---: | ---: | --- |
| pgbench average transaction latency | 58.302 ms | 10.205 ms | **82.4963% lower** |
| pgbench throughput | 68.607777 transactions/s | 391.945622 transactions/s | **5.71285x; +471.2845%** |
| Successful transactions | 2,061 | 11,757 | Different counts at the same nominal duration |
| Failed transactions | 0 | 0 | 0% in each trial |
| Single EXPLAIN execution time | 8.237 ms | 1.095 ms | **86.7063% lower** |
| Single EXPLAIN planning time | 1.330 ms | 1.592 ms | Higher with index; included for completeness |
| Plan shared blocks, hits + reads | 3,138 + 0 | 165 + 5 | **94.5825% fewer block accesses** |
| Matching rows before aggregation | 959 | 959 | Same selectivity |
| Access path | Sequential scan | Bitmap index scan + bitmap heap scan | Uses `idx_claims_claim_date` |

Buffer counts above use the top-level plan totals only; nested plan counts are
not added again. These are shared-buffer accesses, not physical disk I/O saved.
Final index output confirms the date index was restored.

The large latency/throughput difference and reduced plan work make this the
strongest resume-safe optimization measurement **when explicitly scoped to this
local benchmark and bounded daily-report SQL query**. It is still one fixed-order
before/after pair, not repeated statistical proof. EXPLAIN is one execution per
mode and should corroborate, not replace, the longer pgbench measurement. No
SQL p95/p99 was recorded. Do not claim all reporting APIs became 5.71x faster,
or that durable storage, arbitrary date ranges, or production AWS will show the
same gain. The HTTP daily-report endpoint was not benchmarked before/after the
index.

## 6. Resume-safe statements versus claims to avoid

### Strongest, scoped wording you can use

1. **Index optimization:** "Optimized a PostgreSQL daily-report aggregation with
   a date index, reducing average query-benchmark latency by 82.5% (58.3 to 10.2
   ms) and increasing throughput 5.7x in a local benchmark seeded with 100K claims."
2. **Performance verification:** "Built repeatable k6/pgbench benchmarks against
   a 100K-claim, 215K-history-row dataset; observed zero HTTP-status failures
   across 42,958 measured requests at 20 concurrent virtual users."
3. **Caching, with its scope intact:** "Validated Redis cache-aside reads with a
   98.38% hit rate across 20,275 measured requests in a warmed small-working-set
   benchmark against a 100K-claim database."

Prefer the first two if resume space is limited. The third proves effective
cache reuse in that workload, not an application speedup or production hit rate.
The dataset/history sizes refer to the seed; the mixed run subsequently added
105 claims and their history.

### Measured but noisy/inconclusive; do not market as optimization wins

- "Redis reduced p95 by 21% and p99 by 18%": true only of this run's group-median
  calculation, contradicted as a stable effect by paired variation and CPU
  saturation. Keep in the report with caveats, not as a standalone resume win.
- "Redis increased throughput": unsupported; median throughput was 2.28% lower.
- "Reduced database queries by 97.73%": the counter is approximate database
  commits per request, not instrumented SQL query count.
- "Handled 100K claims per second", "cached all 100K claims", or "served 1,000
  concurrent users": false. 100K is seeded database size, 20 is concurrency,
  and the detail-read workload reaches at most 280 selected keys.
- "Zero-error production service" or "100% reliability": a brief synthetic
  run with expected HTTP statuses establishes neither availability nor an SLA.
- "5.7x faster reporting API": measured pgbench SQL throughput is not HTTP API
  throughput, and the comparison applies to one selective query.

## 7. Calculation verification and reproducibility

Run the dependency-free, read-only analyzer from the repository root:

```bash
node benchmarks/analysis/summarize-phase16.mjs benchmarks/results/20260831T045941Z
```

It emits full-precision JSON without rewriting results. It verifies raw custom
request/error counts and linearly interpolated raw p50/p95/p99 against all seven
measured summaries; checks endpoint counts, authentication mode, and CSV values;
and calculates trial medians, paired changes, Redis ratios, CPU counter deltas,
and SQL index differences. All seven measured raw streams passed these checks.
Warmup files are intentionally excluded. Throughput values are taken from k6
summary counter rates and cross-checked against CSV, not reconstructed from an
assumed 60-second denominator.

Only this report and its read-only calculation script were added. No new
benchmark run was performed, no values were invented, and no application tests
were rerun for these analysis-only additions.
